## What the survey does now

**Five MCP servers across four organisations.** Content is generated from your
scanner's own `five_level_v2_policy_v5r_nacombo` results, so the survey asks about the
servers the scanner actually scored.

| Server | Organisation |
| --- | --- |
| Google Calendar | Aurora Airways — commercial airline |
| GitHub | Helios Grid — electricity transmission, NERC CIP, SCADA |
| Slack | Vireo Bio — biopharma, blinded clinical trials |
| Filesystem | CBG — research organisation |
| SQL Database | CBG — research organisation |

**Each participant rates 2 of the 5.** Not random: the two least-covered servers are
chosen, ties broken randomly, so coverage stays within one of even at every point in
the study. Which pair they got is recorded in `assigned_servers`. The survey is 8
sections, not 17. Participants are not told they are seeing a subset.

**Three dimensions per server**, scored one at a time:

| Step | Asks | Shown |
| --- | --- | --- |
| Action Impact | what one call can do | the MCP server only |
| Asset Confidentiality | harm if the information were exposed | the organisation only |
| Consequence Scope | how far one call's result reaches | both |

The context split is deliberate: judging what a tool does should not be coloured by
whose data it is.

**Every rating is 1–5 or "Not sure".** "Not sure" is a real answer, stored as
`unsure`. Consequence Scope cells the scanner says are impossible are pre-filled `N/A`
and read-only — participants score only pairs that exist. Between 79% and 100% of each
matrix is answerable.

Roughly 90–100 judgements per participant, 25–35 minutes.

## Where the data goes

Only **completed** submissions are stored. An abandoned session leaves nothing.

Two tables in Supabase:

* **`responses`** — one row per participant. Metadata columns plus `answers` (JSONB)
  holding every value.
* **`ratings`** — one row per individual rating: `dimension`, `server`, `asset`,
  `tool`, `value`, `value_num`. This is the shape to query.

`value_num` is null for `unsure` and `N/A`, so `avg(value_num)` skips them
automatically.

```sql
select server, tool, avg(value_num) as mean_score, count(*) as n
from ratings where dimension = 'impact'
group by server, tool order by mean_score desc;
```

**Getting a CSV** — either from the results panel (two buttons: *wide*, one row per
participant; *long*, one row per rating) at any time while the app runs, or from the
Supabase dashboard → Table Editor → Export.

Reading a value:

| Value | Means |
| --- | --- |
| `1`–`5` | a judgement |
| `unsure` | participant said they could not judge it |
| `N/A` | the scanner says this tool cannot touch this asset — not a human answer |
| blank | that server was not shown to this participant |

## Operating it

**After a push that changes anything under `survey/`, reboot the app.** Manage app →
⋯ → Reboot app. Streamlit Cloud re-runs `streamlit_app.py` in the existing Python
process on a redeploy, so already-imported modules stay cached and the new code runs
against the old classes. This caused every crash we saw. Pushes that only touch
`survey_config.json` or `streamlit_app.py` are fine without one.

**The app sleeps after 12 hours without traffic.** A sleeping link shows a "Zzzz"
screen and takes about two minutes to wake. The GitHub Action that was meant to
prevent this does not work — Streamlit serves a static shell to plain HTTP, so `curl`
gets `200` whether the app is awake or asleep and never opens the session. A
headless-browser version does work and is recorded in the history if you want it back.
Otherwise: open the link yourself before each recruiting wave.

**Rotate the Supabase secret key.** It went through a chat transcript. Project
Settings → API Keys → roll the secret, then update the Streamlit secret. It grants
full read and delete on every response.

**Remove `showErrorDetails` before recruiting.** `.streamlit/config.toml` currently
shows real tracebacks in the browser instead of redacting them. That was for
debugging; participants should never see one.

## What review found, and what was fixed

Four independent reviews: a beginner reader, and three judges covering rubric
fidelity, survey methodology, and implementation.

### Fixed

**Descriptions were telling participants the answer.** 25 of 64 items failed on this.
`unblinding-requests` said *"revealing it early ruins the trial"*; `api_keys` said
*"one of these is enough to get into another system"*, almost verbatim the level-5
definition; six read tools carried *"No file contents"* / *"Nothing changes"*. Worse,
the hints were uneven — Slack scored 10 good of 13 while Calendar, Filesystem and SQL
were loaded — so a between-server comparison would partly measure the wording. All 35
failing items rewritten; two tests now guard it.

**Four assets were placeholders.** *"Whatever a file read gives back"* gives nothing to
score. One went further and instructed outright: *"It is as sensitive as the most
sensitive file the agent is able to open."* All replaced with concrete content.

**Three descriptions named operations their server has no tool for** (merging a pull
request, creating a folder), and one contradicted its own organisation
(`product-source` spoke of "the version customers actually use" for a research lab).

**Silent CSV corruption.** The local-CSV fallback wrote values positionally under
whatever header was on disk, so any survey change misaligned every value with no
error. It now refuses to append under a mismatched header. This never affected
Supabase.

**The long export silently returned zero records** for rows without an
`assigned_servers` value, while the panel still reported the responses as collected.

**No mutual exclusion on local CSV writes** — concurrent submissions could interleave.
Locks are now per file path.

**A config edit could deadlock the survey** — validation matched problems to a step by
prefix-matching a display label, so two dimensions sharing a label made a page
impossible to pass.

**"Not sure" was missing from Consequence Scope**, the step with the most cells, placed
last, where fatigue is highest. A forced guess is indistinguishable from a judgement in
the data. Now offered there too.

**The rubric was hidden.** Level definitions sat in a collapsed expander with only
levels 1 and 5 labelled. Anyone who did not expand it was answering a bare 1–5
intensity scale. Now open by default, all five labelled.

### Still open — your call

**1. The rubric drifted from what the scanner scores.** You supplied a cleaner
three-dimension rubric; review found it diverges from the scanner's prompts on all
three scales, and the drifts multiply because `score = confidentiality × scope ×
impact`. The main ones:

* Asset Confidentiality asks only about exposure. The scanner asks about *"exposed,
  corrupted or destroyed"* — which strips integrity and availability out of
  `scada-gateway`, `infra-config`, `crew-roster`, `maintenance-schedule`.
* The tie-break is inverted. Scanner: *take the higher* on secrets, PII, regulated
  records. Survey: *take the lower one*.
* Aggregation is contradicted. Scanner raises a tier for whole-population assets;
  survey says *"volume does not change the score"*.
* Consequence Scope level 5 lost three of its four routes — portable credential, whole
  population, destroyed-with-nothing-left. Only load-bearing dependency remains, so the
  scanner's own headline example (reading one password file) has no tier.
* "Permissions" is level 2 for the scanner and level 4 in the survey.

Fixable in config without touching code. It partly reverses your wording, which is why
it is waiting on you.

**2. Does approving a pull request deploy anything** on the Helios GitHub server? The
description currently asserts it does not. If it does, `create_pull_request_review`
moves from level 2 to level 5, and I cannot tell from your data.

**3. Subsample the Consequence Scope matrix?** It is 68–76% of every participant's
judgements, sits last in each server block, and costs 2–3 interactions per cell. 12–15
cells per participant, crossed across participants, would keep full coverage and lose
the fatigued data.

**4. Add an overall risk question?** Without one there is no way to test the composite
`impact × confidentiality × scope` against human judgement — you can validate the three
parts, but not the formula that combines them.

## Limits on the analysis

Worth knowing before writing anything up.

* **`unsure` is not missing data.** People opt out on the ambiguous items — the
  informative ones. Dropping those rows and reporting agreement on the rest inflates
  the figure. Report the per-item unsure rate alongside it, and never impute a value.
* **Exclude `N/A` cells from agreement statistics.** They are your own input echoed
  back; counting them as agreements inflates kappa mechanically.
* **Do not compare levels across servers.** Server is confounded with organisation,
  asset order, the impact range its tools span, and N/A density.
* **Ratings are not independent observations.** They are nested within participant and
  server, and matrix cells correlate along their row and column. Aggregate to item
  means, or use a mixed model.
* **The scanner's reachability model is assumed, not tested.** A pair it wrongly marks
  impossible is invisible — no participant can flag it. Do not describe the scope
  results as validating the tool/asset model; they validate only the cells it admits.
* **Item order is fixed for everyone**, and two servers happen to run in ascending
  severity, so order effects cannot be estimated or averaged out.
